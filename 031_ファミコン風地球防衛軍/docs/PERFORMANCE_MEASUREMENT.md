# PERFORMANCE MEASUREMENT / 1.2.0-A

## 再利用と計測範囲

`AcceptanceMeter`は既存`MobilePlaytest`を継承し、ヒストグラム・CPU集計・資源ピーク・開始／終了を再利用する。従来の連続30秒試験、6秒BENCH、既存Profilerは残す。新しい受入モードだけが中断後の再開・有効時間の積算・20件保存を行う。従来メーターとは結果の意味が異なるため、同一列で混ぜて平均しない。

`game.js`の既存RAFループの更新前・更新後・描画後のPerformance時刻を使用。DEBUGかつLABのプレイ／エンディング時だけ診断を行い、表示更新は750ms間隔。HUDはゲーム外ヘッダーでON/OFFでき、ワールド座標・倍率・当たり判定は変えない。

| 項目 | 定義 |
| --- | --- |
| 現在FPS | 直近最大120個の有効RAF間隔の`1000 × 個数 / 合計ms`。中断時は窓を空にする |
| 有効平均FPS | 全有効間隔の`1000 × samples / acceptedDurationMs`。瞬間FPSの算術平均ではない |
| 低FPS指標 | `1000 / p95 RAF間隔`。絶対最低FPSや一般的な1% lowではない |
| P50／P95 | 有効間隔の順位統計。0.25ms刻みヒストグラムの上端値（最大0.25msの量子化） |
| updateCPU／drawCPU | それぞれのJS処理実行時間の平均。RAF間隔・GPU実行・画面表示完了とは別 |
| 有効時間 | 受理したRAF間隔の総和。非表示・ポーズ・準備時間を含まない |
| 経過時間 | 最初の観測RAFからの壁時計的経過。中断を含むため有効時間と別表示 |
| 敵数 | `liveEnemies`。死亡演出は生存敵へ数えない。現在値と試験中ピーク |
| 弾・FX | プレイヤー弾＋敵弾、通常FX＋impact粒子。上限管理された既存配列を参照 |
| 文脈 | 開始／終了のミッション・AREA・性能プリセット・装備・密度・上限・無敵・Canvas内部解像度・倍率・音声状態・ミュート／音量・viewport |

CPUが取得できないサンプルを含む場合、そのCPU集計は未取得。未計測FPS・温度・メモリ・GPU時間を0や推定値で埋めない。ブラウザUAは取得可能な文字列で、正確な機種判定ではない。

## 受理・除外・中断

1. `document.visibilityState`／hidden、focus、プレイ状態を確認。非表示・ポーズ・LAB操作中を集計しない。[Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)の通知に加え、pagehide／pageshow、blur／focus、向き変更も中断扱い。
2. 開始・復帰後の最初のRAFは差分基準点だけとし、その後1秒のウォームアップを除外する。復帰直後の古い時刻差を加算せず、直近FPS窓も初期化する。
3. 正の間隔が250ms以下なら、100ms=10fps・250ms=4fpsも保持する。遅いという理由だけで除外しない。
4. 250ms超は長間隔として必ず回数・詳細を記録。直前コールバックの更新＋描画CPUが間隔の75%以上を説明し、間隔が2秒以内なら`CPU_LOAD`として有効集計へ残す。後続コールバックのCPUで過去の空白を説明しない。
5. 説明できない長間隔は`UNRESOLVED_LONG_GAP`として時間・回数を残して除外し、再準備する。これはバックグラウンド停止とも実性能低下とも断定しない。3回以上連続すれば継続遅延疑いを表示し、都合のよいFPSとして評価しない。
6. 非単調時刻・停止中などの除外回数、準備除外、基準点除外、中断回数を別記。中断通知が重なっても再開待ち状態での重複計上は避ける。

250msは停止検出の目安であって合格ラインではない。2秒超の継続負荷が実際に起きても原因判定不能となる場合があるため、その記録を隠さずPhase Bへ引き継ぐ。ブラウザ自動操作による停止とゲームCPU負荷を完全に識別できるとは主張しない。

## 品質判定

| 表示／JSON | 条件と解釈 |
| --- | --- |
| 測定不成立／INVALID | 有効30サンプル未満、または有効1秒未満。FPSによる比較をしない |
| 参考値／REFERENCE | 最低条件は満たすが目標時間不足、または中断・判別不能な長間隔あり。前景連続性能の保証に使わない |
| 成立／VALID | 目標有効時間を満たし、中断・判別不能な長間隔なし。CPU整合の実際の低速フレームを含み得る。速い／合格の意味ではない |

目標は30／60／120秒。手動停止は30秒以上で品質判定するが、120秒長時間受入を満たしたかは有効時間を別途見る。現在FPSは中断直後「未取得」、平均は受理済みデータを保持。人手の通常攻略手動記録は`MANUAL_ENTRY`・計測なしで、FPSは未取得、通常クリア自動認定はfalse。

## 保存・出力と上限

- 保存キー：`pixel-defense-front-acceptance-v1`。通常セーブキーとは別。履歴20件、各問題12件、重要イベント32件、保存JSON合計240,000文字の防御上限。CPU・ヒストグラム・最近120フレームの配列は保存しない。
- 同一セッションを部分保存→停止しても同じ記録を更新。終了／ページ離脱時に集計を保存する。履歴容量超過は古い記録から削除するため、必要な記録を先にエクスポートする。
- localStorage読込／容量エラーは診断ステータスに表示。通常セーブを初期化しない。保存不可でもメモリ内結果とコピー出力は使える。
- JSONは履歴全体、テキストは選択記録の集計・人手評価・問題。外部送信なし。ファイル保存は要求した事実だけ表示し、Safariで保存済みとは断言しない。自動コピー失敗時の読取専用テキスト欄を用意する。

## 実機計測手順

1. [LAN接続手順](MOBILE_ACCEPTANCE.md)で実機を接続し、環境・電源・画面方向・音声・解像度・密度・演出を記録する。
2. 50／100／200体を既存「敵・ボス」で用意（200はLAB限定）。同じ武器・兵科・カメラ・演出で「現在の戦闘で計測開始」。必要なら30→60→120秒で比べる。
3. 開始後は前景で操作し続ける。LABを開くと計測中断になるので、診断HUDで状態を見る。正常な連続区間が得られない場合は無意味に再試行せず、理由と有効件数を残す。
4. 停止して品質・有効秒数・除外・長間隔・最大敵数を確認。平均FPSだけでなくP95・CPUと、実際に射撃／爆発していたかを併記する。
5. JSON／テキストをコピーし、音声・入力・視認性の人手評価を付ける。別条件の数値を混ぜない。iPhone以外の値をiPhone性能と表現しない。

今回のChrome結果は[参考記録](../reports/mobile-acceptance/README.md)。IP-07は有効0件で測定不成立、IP-01/IP-10は参考値。50／100／200体のiPhone実機比較・熱変化・長時間連続性能は未測定であり、60fps保証はしない。
