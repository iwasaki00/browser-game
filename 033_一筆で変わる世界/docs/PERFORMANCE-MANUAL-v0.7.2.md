# Chrome DevTools Performance 手動解析手順 — 0.7.2

作成日: 2026-10-22。今回の操作ツールにはDevTools Performanceの記録・Mainタイムライン取得機能がないため、**Performance解析は未実施・未確認**です。以下は実施方法であり、解析済みの結果ではありません。

## 準備

1. Windows Chromeで試験用のページを開きます。開発サーバーを `npm run dev -- --host 127.0.0.1 --port 5189 --strictPort` で起動し、表示URLに`?quality=1`を付けます。PCでの検証手順です。実機へは[LAN/静的配信手順](DEVICE-ACCESS-v0.7.1.md)を使います。
2. OS版・Chromeの「Google Chromeについて」に表示される完全版、解像度・Viewport・DPR、電源・節電、ウィンドウの見え方、他アプリ、操作ツールの接続有無を記入します。版が不明なら未取得のままにします。
3. Stage 01、通常表示、流向OFF、速度20、ズーム1倍を基準にします。新しい変更は読み込みを終えてから計測をリセットし、ホットリロードを測定へ混ぜません。
4. F12でDevToolsを開き「Performance」を選びます。CPUスロットリングは変更なし、ネットワークも通常条件に揃え、設定値を記録します。記録自体の負荷があるので、診断だけの試行とは別に扱います。

## 記録する

1. Performanceの録画ボタンを押す（一般的にはCtrl+Eでも開始/停止）。再読み込みを伴う録画と通常録画は区別してください。
2. ゲームの地図か操作をクリックしてページへフォーカスを戻し、診断のvisibility/focusを確認します。DevToolsへフォーカスがある期間は前面A条件に数えません。
3. 停止表示を観察してから「一筆なしで実行」を押し、120ステップまで再生します。PLAYINGとPAUSED/RESULTの境界は診断JSONの`segments`に記録されます。録画全体を再生性能の統計に使わないでください。
4. 約1秒の間隔が見られた時刻をメモします。終了後に録画を止め、「結果をテキスト表示」で同じ試行のJSONもコピーします。録画を止めるためにDevToolsへ移動した期間を測定対象から外します。
5. トレースを保存し、版・条件・試行番号を付けます。同じ手順を可能なら3回繰り返し、操作ツール接続あり/なしを分けます。終了後の長い静止時間をPLAYING区間へ混ぜません。

## 約1秒の区間を拡大して見る

1. FramesとMainトラックを表示し、該当時刻の前後をドラッグして拡大します。診断JSONには`performanceTimeOriginMs`と相対時刻があり、`events[].atPerformanceMs`・RAF時刻・`segments`の開始終了を照合できます。
2. Mainにその空白を埋めるタスクがあるか調べます。長いタスクを選び、Summary・Bottom-up・Call treeで実行内容を確認します。JavaScriptの関数名、Scripting、Recalculate Style、Layout、Paint、Composite、GCなどの時間を記入します。
3. RAF実行イベントが連続しているか、登録後にコールバックまで空白があるかを確認します。ゲーム診断の`lifecycle`ではゲームのコールバックを関数参照で識別し、他のRAFと分けています。全RAF待機数だけをゲームの多重起動と解釈しません。
4. `LONG_INTERVAL`の`intervalMs`と`previousCallbackCpuMs`・`callbackCpuMs`を比較します。これらCPU値はゲームのJavaScriptコールバック内の経過時間です。Style/Layoutやブラウザー/OSの待機をすべて含む値ではありません。
5. 例外がある場合はConsoleの時刻と`CALLBACK_EXCEPTION`を照合し、その後も次回RAFが登録されているかを確認します。次回登録前の例外による永久停止と、繰り返す約1秒間隔を区別します。
6. 非表示・復帰・フォーカス喪失・メニュー・PAUSE・終了後の区間でなかったか、診断の条件と操作状態を確認します。取得できなかったトラックは未確認とします。

## 解釈の基準

| 観測 | 支持する候補 | まだ言えないこと |
| --- | --- | --- |
| Mainが長いJS/描画/GCで埋まっている | A ゲーム等の長時間処理。コールスタックで所有元を特定する。 | RAF間隔全体をCanvasや水流だけの責任にできない。 |
| 次回RAF登録がなく例外が残る | B 登録に到達しない経路。 | その例外が今回の1秒間隔を起こしたとは限らない。 |
| RAF要求は残り、Mainが空いて見える | C ブラウザー/OSの発行遅延の候補。 | 他トラック・OS・記録漏れを調べる前に内部理由を断定できない。 |
| 停止後の時間、別RAF、条件境界が混入 | D 計測の不備。区間・対象を分離して再測定する。 | 計測を直すだけで実際の遅延が解消したとは言えない。 |
| 証拠が不足、複数候補が残る | E 原因未特定。 | 推測によるレンダラーや計算式の変更は行わない。 |
