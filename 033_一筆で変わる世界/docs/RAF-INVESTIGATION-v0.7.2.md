調査日: 2026-10-22。調査と診断の補強が対象です。水流・一筆・ステージ・比較計算・保存・レンダラーの仕様は変更していません。実測結果は[統制計測記録](RAF-MEASUREMENTS-v0.7.2.json)、結論と未実施項目は[品質報告](QUALITY-REPORT-v0.7.2.md)に分けています。

## 登録と状態遷移

`src/main.ts`の初回`update(); requestAnimationFrame(frame)`で開始します。`frame`は診断の有無に応じて`runFrame`を1回呼び、`runFrame`末尾で次を予約します。

| 経路 | RAFの動作 | 論理計算・描画 |
| --- | --- | --- |
| メニュー画面 | 次回1件を予約してreturn | 計算・地図描画をスキップ。メニューを開く時点でランナーを停止。 |
| 比較画面 | 比較処理後、次回1件を予約してreturn | 同じ比較コントローラーをadvanceし、必要時だけ描画。表示切替は新ループを作らない。 |
| 通常画面 | 関数末尾で次回1件を予約 | playingの時だけadvance。dirtyか流向アニメーション条件を満たす時だけ描画。 |
| PLAY / PAUSE | 登録箇所を呼ばない | ランナーの再生フラグを切り替える。PAUSEはRAF自体を止めない。 |
| RESET / ステージ変更 | 新規RAFを開始しない | 旧ランナー停止・試行を初期化/新規生成。既存の1本のRAFが参照する状態を替える。 |
| タブ非表示 / blur | RAFキャンセルを呼ばない | ポインターを解除し単独・比較を停止。RAFの実発行頻度はブラウザー側の制御も受ける。 |
| 前面復帰 | 自動PLAY・新規RAF開始を呼ばない | 停止を維持。診断は復帰1000msと境界を通常値から分ける。 |

3つの再登録箇所は排他的な分岐です。ゲーム本体に`cancelAnimationFrame`の呼出しはありません。別の再生setInterval/setTimeoutも作っていません。診断の表示失効タイマーは単発で論理計算を呼びません。

`core/runner.ts`、`game/playable.ts`、`core/trial.ts`、`comparison/controller.ts`、`comparison/view.ts`、`input/visibility.ts`、`quality/raf.ts`、`quality/metrics.ts`、`quality/environment.ts`、`quality/deadline.ts`と関連テストも確認しました。

[ソース照合](PROTECTED-SOURCES-v0.7.2.json)で、0.7.1から**mainのフレーム関数・3分岐・初回予約を含むブロックが同一**であることと、保護対象16ファイルが同じGit blobであることを確認しています。比較ビューへの追加は再生フラグの読み取り専用getter、mainへの追加はDEV診断の状態読取りと接続です。

## 例外による永久停止リスク

通常の操作・単独advanceは`safely`で停止表示へ移ります。しかし`drawWorld`、比較の`advance/draw`、内部の結果集計などは、次回RAF予約より前に例外が外へ抜け得ます。その場合は次回登録に到達しません。初期`update()`が失敗した場合も初回登録に到達しません。

これはソース上確認できる停止経路です。単体試験では「予約前のコールバック例外→残待機0→診断にも例外記録→自動再開しない」を再現しました。実ゲームでこの例外が起きた証拠は今回の測定ではなく、**繰り返す約1秒間隔の原因と同一視しません**。ゲームの例外処理や予約順序を推測で変更していません。

## 診断の補強

- `RafActivity`で場面・画面・再生状態・試行phase・比較・表示・流向・速度を記録。状態変更で区間を閉じ、再生中と停止後を混ぜません。条件/活動の境界間隔は別集計です。
- 正式な数値は`segments[].intervals`から取得します。直近最大240間隔の同じ母集団で中央値・p95・p99・最大・閾値件数/割合を返します。累積件数は別欄です。240件を超える場合、窓の分布を累積全件の分布と表記しません。
- >100/>500/>900msは厳密な超過です。最長連続異常期間は、連続する>100ms間隔の合計時間。CPUのLong Task長ではありません。区間境界で連続を切ります。
- `RafLifecycleProbe`はDEV限定で既存RAF APIを転送し、要求ID、世代、時刻、活動、visibility/focus、長い間隔、直前/当該ゲームコールバックCPU、例外を最大120イベントに保存。consoleへ毎フレーム出力しません。頻度の集計はイベント保持上限とは独立です。
- mainから実際の`frame`関数参照を渡してゲームのRAFを識別します。初回導入前の予約は観測外です。別の匿名RAFの同時待機を、ゲームの多重起動へ数えません。
- OFFは元APIを復元し、予約済みコールバックを取り消しません。再ONも新しいゲームループを作りません。例外の自動再開・抑止・再登録の重複排除は行いません。

## 原因候補の分類

| 分類 | 支持する証拠 | 反証・限界・未確認 |
| --- | --- | --- |
| A ゲーム等の長時間処理 | 描画/集計/診断/GCが遅くなる可能性はある。 | 新測定の時刻対応コールバックCPUと間隔を比較。MainのStyle/Layout/Paint等のトレースは未取得で、全区間を否定できない。 |
| B 登録・停止・再開 | 予約前の未捕捉例外は永久停止し得る。 | 実測中のゲーム待機数・例外数を別確認。再生操作から多重登録する経路はソースでは見つからない。永久停止経路だけでは周期的1秒を説明しない。 |
| C ブラウザー/OS | コールバックCPUが短いのに発行間隔が長い場合は候補。 | Mainが空いていたか、遮蔽・節電・操作ツールの影響かは未確認。visible/hasFocusだけでOSの物理前面を断定できない。 |
| D 計測ロジック | 0.7.1は活動別の区切りがなく停止前後を混ぜ得る。全RAFにはゲーム以外の匿名コールバックも実在した。 | 区間分離・関数参照識別を修正。過去の個々の1秒間隔すべてを計測誤りと断定することはできない。 |
| E 未特定 | 内部トレース・統制したB/C/D・接続なしの比較が不足。 | 約1秒の内部原因は未特定として残す。複数原因の併存も排除しない。 |
