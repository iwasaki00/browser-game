# 状態別の性能計測手順 — 0.7.1

作成日: 2026-10-22。[0.7.0の7場面の手順](PERFORMANCE-PROCEDURE-v0.7.0.md)を引き継ぎ、RAFを条件別に記録します。単独計算、Canvas描画、A/B同期、RAF間隔は別の指標です。RAF間隔だけから計算が遅いとは判定しません。

## 準備

Windows Chromeで、試験用の別オリジンまたはプロファイルを使います。通常の進捗は初期化しません。開発サーバーを起動して表示URLへ`?quality=1`を付けます。

```sh
npm run dev -- --host 127.0.0.1 --port 5188 --strictPort
```

ヘッダーがv0.7.1であることを確認します。OS完全版、Chrome「Google Chromeについて」の完全版、CPU・メモリー、電源・省電力、画面解像度、Viewport、DPR、拡大率、他アプリ・拡張機能、診断の開閉を記入します。UAや別のChrome実行ファイルの版を、実行中ブラウザーの完全版と同一視しません。

「測定条件を記入」に環境と試行名を入れます。「結果をテキスト表示」でJSONをコピーできます。結果欄を閉じて再表示すると新しい時点のJSONになります。パネルの詳細を閉じても計測します。静的配信には診断コードが入らないので、通常プレイと実機の受入試験は既存配信で、診断は開発用URLで行います。

## A〜Dの定義と境界の扱い

| 条件 | 記録上の条件 | 開始と終了 |
| --- | --- | --- |
| A 前面 | visibilityState=visible、hasFocus=true、復帰区間外 | 環境イベント/RAFで確認して開始。非表示・フォーカス喪失・診断停止で終了。 |
| B 非表示 | visibilityStateがvisible以外 | visibilitychange等で開始。可視状態に変わると終了。RAFが来なければ有効サンプル0・値null。 |
| C フォーカス喪失 | visibilityState=visible、hasFocus=false | blur等で開始。非表示またはfocusで終了。移動先アプリは別途手動記録する。 |
| D 復帰直後 | B/Cからvisible+focusへ戻った後1000ms | 最初の1000msを隔離。通常統計へ移るには次のRAF観測が必要で、RAF停止中は「復帰待ち」のまま。 |

同じ条件が両端で連続観測された間隔だけを、その条件の分布へ入れます。条件の境界をまたぐ間隔は`boundaryIntervals`へ隔離します。復帰最初のRAFまでの間隔は`firstResumeGaps`にも記録しますが、これは非表示期間・停止期間を含み得る空白であり、復帰後の描画CPU時間ではありません。両項目は一部重複する分類なので足し合わせません。

環境イベントは`visibilitychange`、`focus`、`blur`、`pageshow`を観測し、RAF側でも実状態を読みます。フォーカスが動いた先やOSの実ウィンドウ遮蔽はブラウザーAPIだけでは確定できません。Aとして約1秒が記録された場合も捨てずに残し、同時刻の外部条件を調べます。

各条件について次の2種類を区別します。

- `conditions.<条件>.window`: 直近最大240間隔の**同じ母集団**の件数・平均・中央値・p95・最大・100ms超回数。中央値は偶数件なら中央2件の平均、p95はnearest-rank。
- その外側: 計測リセット以降の累積件数・平均・最大・50ms超/100ms超回数。直近中央値と累積平均を同じ母集団として比較しません。

`segments`に開始/終了のperformance.now基準時刻、実際のvisibilityState/hasFocus、開始/終了理由を最大120区間残します。破棄した区間数も出します。終了nullは取得時も区間継続中です。`performanceTimeOriginMs`に相対時刻を足せばUTC時刻へ対応できます。全期間の状態・全フレームの配列は保存しません。

通常FPSはAの現在区間だけから計算します。直近RAFから1000ms以上経過した場合、非表示、フォーカス喪失、復帰待ち、診断停止では現在FPSをnull/未取得にします。診断専用の単発タイマーを最大1件使って古い表示を失効させます。これはゲームを進める再生タイマーではなく、繰返しを自動生成しません。ブラウザーがタイマーごと停止した場合も画面の値は「最終観測時の値」と明示し、更新停止中の現在FPSを保証しません。

## 4条件の手動測定

1. ホットリロードやウィンドウサイズ変更が落ち着いてから計測をリセット。Stage 01、停止、通常表示、流向OFF、ズーム1倍を基準にします。
2. **A**: Chromeのゲームタブを選び、ゲーム内をクリックし、別アプリを触らず30秒表示。visibility=visible、hasFocus=trueを確認。結果を出力します。
3. **B**: 計測を続けたまま別タブを選び30秒待ちます。ゲームを背景へ送った時刻を記録。戻って出力し、B区間のcontext・期間を確認します。RAF0件は未測定であり0FPSではありません。
4. **C**: ゲームを見える位置に残し、メモ帳等の別アプリをクリックして30秒待ちます。完全に隠す/最小化した場合はBと混ざる可能性があるため、実際のvisibilityを優先します。戻って出力し、別アプリ名と時刻をメモします。
5. **D**: B/Cから戻った直後の1秒と最初の復帰間隔を確認。ゲームは既存仕様通り停止したままです。戻るだけでPLAYされないことを確かめます。
6. 同条件で可能なら3回繰り返します。操作ツール接続あり/なし、DevToolsあり/なしは別試行として記録。読み込み直後と安定後も分けます。

| 未記入 | A | 未取得 | 未記入 | 未取得 | 未取得 | 未取得 | 未取得 | 未実施 |
| 未記入 | B | 未取得 | 未記入 | 未取得 | 未取得 | 未取得 | 未取得 | 未実施 |
| 未記入 | C | 未取得 | 未記入 | 未取得 | 未取得 | 未取得 | 未取得 | 未実施 |

## 計算・描画・入力の切り分け

- Stage 01の一筆なしを120まで再生し、単独ステップCPUとCanvas CPUを別記録。再生終了後に待った期間を再生中FPSと混ぜず、Step到達直後のJSONを採取します。
- 成功する一筆をプレビュー→A/B比較で120まで再生。同期ペアCPUはA+Bを1組として記録。PLAYのバッチ平均と個別ステップ最悪値を混同しません。A/Bが同じStep、収支差0も確認します。
- 一筆の入力→線・プレビュー表示までの反応を人が観察します。マウス/指、倍率、入力方法、キャンセル、遅延が毎回かを記録。CPU描画時間から指の応答遅延を推測しません。
- 必要ならChrome DevToolsのPerformanceで記録を開始し、問題を再現して停止。Mainの長いタスク、Scripting/Paint/Rendering、タブ切替時刻を照合します。記録のオーバーヘッドがあるため診断だけの試行と分けます。取得しなければ長時間タスクは未測定とします。

## 連続操作

6面切替、同面10回以上リトライ、チャレンジ/フリー往復、PLAY/PAUSE/STEP/RESET、BEFORE/AFTER、パン/ズーム、メニュー、非表示/復帰を反復します。試行回数と実時間を残します。実機は既存の15分以上の試験も維持します。

確認は、勝手なStep進行なし、二重再生なし、ポインター残留なし、A/B一致、収支差0、描画継続、エラーなし。DOMなしの制御モデル反復テストでは、実ブラウザーのタイマー/描画停止や指の操作感まで合格にしません。実機接続は[実機アクセス手順](DEVICE-ACCESS-v0.7.1.md)、記入は[既存30項目](MOBILE-ACCEPTANCE-v0.7.0.md)を使います。
