# v0.7.2 — PHOTO PICKER FIX / 画像選択修正

2026-11-09。画像選択経路を修正し、ソース版／公開成果物版で検証した。**CONDITIONAL：報告されたiPhone端末での解消確認は待ち。v1.0.0更新・本番切替・デプロイは行っていない。**

## 原因の確定範囲

**報告端末の原因は未確定**。v0.7.1の「hiddenのinputへclick()することがSafariで無効」と断定する根拠は得られていない。

修正前のv0.7.1をHTTPのサブディレクトリで起動し、既存の実ボタンから `filechooser` を待って選択したところ、Chrome 157.0.8103.38／WebKit 26.4とも3件の調査試験が成功した。[Chrome原状調査](qa-v072/baseline/chrome.json)、[WebKit原状調査](qa-v072/baseline/webkit.json)。Chromeは変更前の作業ソース、WebKitはGitのv0.7.1スナップショットを利用した。これは本番URLや報告端末で再現した結果ではない。

|調査項目|確認できたこと／限界|
|---|---|
|ボタンのclick登録・実行|v0.7.1のボタンからfilechooserが発生したため、調査したブラウザではハンドラーが実行された|
|inputの取得|filechooserの対象が唯一の `#image-input` であり、画像選択後に表示された|
|hiddenへのclick|v0.7.1ではhidden=true、display=noneでも上記2エンジンで成功。iPhoneの全条件へ一般化しない|
|起動例外・アセット|正常なHTTP試験ではpageerrorとアセット読込エラーは0。報告端末のキャッシュ・起動ログは未取得|
|ハッシュ付き参照|修正後の公開成果物でJS／CSS／SVGの読込と大小文字・相対パスを確認。ソースへの補完なし|
|透明要素・Canvasの重なり|実クリック／タップ前に中央点のelementFromPointで対象が覆われていないことを検査|
|fileプロトコル|動作試験はHTTP。file://の成功と混同しない。起動診断はfile:ならHTTP(S)利用を案内|
|Safariのユーザー操作制限|タップはネイティブlabel、キー操作は同期処理。Playwright WebKit合格はiPhone実機合格を意味しない|

確定した問題は、旧ブラウザ試験の `setInputFiles()` だけではボタンからのファイル選択を保証できなかったこと。今回、実操作→filechooser→ファイル指定という経路を独立した必須試験にした。

また、標準labelへ変更するとJS起動前にも選択可能になるため、初期化前に選ばれたファイルを取り込む処理を追加した。この順序については、追加内部試験が実装前に失敗（写真が表示されない）、実装後に成功した。ブラウザでもappスクリプトの読込を一時保留してから画像を選択し、起動後に表示されることを検証した。これを元のiPhone不具合の確定原因とは扱わない。

## 修正内容

- `index.html`：「画像を選ぶ」「画像変更」を同じ `#image-input` に関連付けるlabelへ変更。inputのhidden属性を撤去し、視覚的に隠すクラスへ変更。操作IDは維持。
- `style.css`：labelを既存のボタンと同じ外観・44px以上の対象にし、フォーカス表示と視覚的非表示のinputを定義。
- `startup.js`：ゲームモジュールより先に実行。Tabで到達するlabelのEnter／Spaceを同期的に処理し、起動失敗と選択画面を開く際の例外を専用メッセージで示す。エラー内容・ファイル名・写真は出力しない。
- `app.js`：タップ用の `input.click()` 中継を撤去。既存のchange処理を関数化し、初期化前の選択も取り込む。完了時に起動準備表示を隠す。
- 写真読込本体、2048px上限、向き、旧写真保持、Object URL解放、写真変更後のリセットは維持。Fileを取得後にinput.valueを空へ戻すため、同じ画像の再選択もchangeになる。無選択は状態を変える前にreturnする。
- キャラクター・ポーズ・塗装・コピー・拡大・履歴・PNG合成・答え表示・共有の基本処理は変更していない。

## 実操作の画像選択8試験

1. 初期画面の見えている「画像を選ぶ」を実クリック→filechooser発生→実PNGを指定→写真表示。
2. 「画像変更」も同じinputのfilechooserを発生。同じPNGを再選択すると、編集済みサイズ20%が初期18%へ戻り、change処理の再実行を確認。
3. appスクリプトの配信を保留した状態でもネイティブlabelから選択し、配信再開後に写真を表示。
4. Tabでlabelに到達し、Enter／Spaceでfilechooser発生。タップでも同じ経路を確認。
5. 塗装後に開いたchooserへ無選択応答を返し、DOMのcancelイベントも送信。写真の画素ハッシュとUndo履歴を保持。
6. 実「画像変更」から破損PNGを指定。画像読込エラーを表示し、元の写真・塗装・Undoを保持。
7. 正常時にpageerror／HTTP読込エラーなし。inputは1個、タップ対象は他要素に覆われていない。
8. app／paintの読込を意図的に失敗させると「アプリを起動できません」と表示。JPEG／PNG形式エラーとは区別され、その状態でもネイティブlabelからfilechooserが発生。

試験で使用するPNGは既知色の合成画像。実OSのダイアログを閉じる操作そのものはPlaywrightの無選択応答で代替しているため、**実際のiPhoneのキャンセル操作は未確認**。画像選択8試験は `setInputFiles()` でボタンを迂回しない。既存の一般編集試験には直接設定を残しているが、それを選択ボタンの合格根拠にはしていない。

## プライバシー・残課題

画像処理は端末内のFile／Blob／Canvasのみ。自動外部送信、外部API、CDN、解析、クラウド保存、永続保存は追加していない。起動診断は固定文だけで、ファイル名・画像・エラー詳細をログや画面へ出さない。JS無効時にはnoscriptで編集にJavaScriptが必要なことを案内する。
