# 保存最適化 — Version 0.6.0

## 原因と移行

従来はcollectedTreasuresやrevenueHistoryが個体ごとに増え、二重支払い判定が全履歴に依存していた。v0.6.0は小さい旧セーブをそのまま受け入れ、履歴が閾値を超えた時点で厳密な報酬台帳へ移行する。saveVersion2、FN、能力、所持品、図鑑、未処理バッチを維持する。

最近の回収・契約・収益・選別・回収イベントは各200件、ジャックポット・特別採取地点100件へ制限する。過去の回収数・分野別／お宝別収益・図鑑・累計値は集計として保持する。直近60秒のFN/分は時刻別集計で保持し、高速連続報酬でも履歴切り捨てによって変化しない。未受取品や途中作業は履歴上限の対象にしない。

## 厳密な二重支払い防止

履歴は表示用であり、支払い資格ではない。新個体にはプレイヤー固有接頭辞＋v6＋単調増加の連番を発行する。発行上限と未決済の連番集合を保持し、確定時に資格を削除する。退役番号は再発行しないため、古い支払済みIDを再提示しても報酬を得られない。

旧IDは移行時に実在する未払い個体だけを厳密な許可集合へ封印する。履歴にない任意の旧IDを後から資格集合に足さない。移行時の支払済みIDは対象外。支払済みであっても現存する砂利バッチが参照する旧IDは、そのバッチが不要になるまで正確な参照記録を保持する。区画破棄で未回収個体を退役させ、保存検証では重複個体や退役済みの未受取品を拒否する。近似判定は使用しない。

## 保存の一貫性

変更後の台帳と在庫を同期的にstructuredCloneし、localStorageへ緊急バックアップ、IndexedDBへ順序付き保存する。saveSequenceで新旧を比較し、保存リビジョンのCASで古い書き込みを拒否する。保存待ち中の進行でスナップショット内部が変化しない。新しい緊急バックアップを遅い旧IDB完了で上書きしない。

IndexedDBの同一トランザクションで文書固有の所有者と8秒リースを検査する。1.5秒ごとに更新し、一つのタブだけが進行・保存を担当する。他タブは「このタブで再開」から期限切れ／解放後に最新セーブを再取得する。再読込は同じタブの引継ぎを許可するが、新しい文書IDにより旧pagehideが新所有者を解放することを防ぐ。複製されたsessionStorageだけでは新規タブに権限を与えない。

## 検証結果

- 10,000件旧履歴のブラウザ試験：847,069→27,176 bytes、約96.8%削減。累計10,000件と未処理砂を維持。
- 進行中保存、最新緊急スナップショット、2タブの進行拒否、所有権移動・再読込を確認。ブラウザエラー0。[Phase 0結果](save-phase0-v060.json)
- 24ゲーム時間・3分野同時・毎時再読込：累計9,150件、最近200件。保存最大144,074 bytes、24時点143,831 bytes。1時点141,731 bytesから無制限増加なし。[長時間結果](line-stress-v060.json)
- 非表示24時間分のtickは状態不変。再移行を二重実行しても同一状態。

保存容量は未受取品・途中材料の実数には依存する。安全性のため未受取在庫を黙って捨てない。大規模在庫のさらなる圧縮は次版の検討事項。
