# すれ違い郵便局 — SORT & SEND

Version **0.5.0-B — HINT**。分岐の循環パターンを設定し、荷物を同じ色・印の出口へ届ける戦略パズルです。全20ステージに専用の3段階ヒント、合計60件を追加しました。通常配送・Solver・コスト・採点・RESCUE・履歴・進行保存・音声の既存ルールを維持しています。

## 開発環境・起動

Node.js 20.19以降または22.12以降の対応版、npm、TypeScript、Vite、Canvas 2D、HTML/CSS、Vitestを使用します。大型フレームワークは使用しません。

```sh
cd sort-and-send
npm ci
npm run dev
```

表示されたURLをブラウザで開きます。

```sh
npm test           # 配送・構造検証・探索・コスト・採点の関連テスト
npm run typecheck  # TypeScript型チェック
npm run validate:hints # 60件のヒントデータと参照・成功設定の整合性
npm run build      # 保存レポート整合性検証 + 型チェック + Productionビルド
npm run preview    # ビルド結果の確認
```

`sort-and-send/dist/` が静的配信用成果物です。従来どおり成果物も管理対象とし、更新時はソースと一緒に反映してください。browser-gameの公開リンクとURLは変更していません。外部サービスへの接続は不要です。開発サーバー単体では親の一覧を配信しないため、一覧との往復確認はbrowser-game全体を静的配信して行います。

## 維持したRESCUEの使い方

1. 分岐の循環パターンを設定して「配送開始」を押します。
2. RUN中に「RESCUE / 次の分岐を変更」を押すと、現在の移動が終わるtick境界で一時停止します。移動途中へ割り込んだり、過去の位置へ巻き戻したりしません。
3. ダイアログに次の対象の荷物番号・色・分岐・tick・パターン枠・通常方向を表示します。tickは履歴と同じ0始まりです。
4. LまたはRを選び「確定して再開」を押すと、そのイベント1回だけを指定方向へ変更します。通常方向と同じ方向の確定でも1回を消費します。
5. 「キャンセルして再開」またはEscでは使用権を消費せず、停止した境界から通常配送へ戻ります。

RESCUEは1RUNに1回だけです。パターン自体は変更せず、対象分岐カウンターも通常どおり1回進みます。確定後は使用済み表示となり、残りの配送は元のパターンで続行します。この先に分岐がない場合は使用できない理由を表示します。

プレビュー中は配送tick・荷物位置・カウンター・履歴が停止し、分岐編集・ステージ変更・再挑戦・進行初期化は受け付けません。再挑戦では設定を保持し、カウンター・履歴・RESCUE使用権・予約を新しくします。ステージ変更・初期設定へ戻す操作も以前のRUNを破棄します。RUN途中の中止ボタンは今回追加していません。

### 状態・先読み・識別

`src/simulation.ts`の`DeliveryRun`が1tick単位の既存配送ルールを実行します。`simulate(stage, patterns)`は同じエンジンを最後まで実行する従来の入口で、Solverは引き続き通常配送だけを探索します。

本番状態はtick、荷物の経路・配送先、分岐カウンター、イベント履歴、RESCUE使用状態・予約を保持します。荷物の出発済み状態はtickとID順の出発時刻から決定できます。`clone()`はステージ・設定・本番状態を独立コピーし、コピー上だけで次の分岐まで進めます。検証済み有向非巡回グラフの荷物数＋ノード数を探索上限とし、対象がなければ返しません。

対象は`tick + parcelId + switchId`で識別します。各荷物は1tickに最大1回しか移動しないため、この組で一意です。同一tick内は従来どおり荷物ID昇順です。プレビューは発行したRUNと状態リビジョンに結び付け、確定時に対象・通常方向・枠を再照合します。古い／別RUN／改変したプレビューは確定せず、期限を過ぎた予約は失効させて別イベントへ流用しません。

Canvasは状態コピーから作った予測結果を描画するだけです。本番は完了したtickだけを確定し、プレビュー中はアニメーションフレームを予約しません。確定後も本番の履歴を保持したコピーから残りを再計算し、最終結果は本番エンジンから取得します。UI側で経路を計算しません。

### 星評価・保存・履歴

- FAILEDは星0、RESCUEを確定したCLEARは星1。RESCUEなしの星2・星3は従来どおりです。
- RESCUE成功は通常Solverの成功集合外になり得るため、星1は通常解の最適コスト・分布との照合より先に判定します。方向転換コスト自体は元の循環パターンと実際に使った分岐から計算します。
- 星1のCLEARでも次面を解放します。最高星3の後に星1でクリアしても記録を下げません。保存スキーマとキーは変更していません。
- 結果にRESCUE未使用／使用済みと対象を表示します。荷物別履歴の上書きイベントには通常方向→実際の方向を表示し、該当する経路を金色で強調します。
- 使用RUNは結果の`rescueUsed: true`、上書きmoveイベントは`rescue: true`と`originalDirection`で識別できます。同方向の確定も記録します。将来の研究室はこのフラグで除外できます（研究室は未実装）。

### 進行保存・設定・初期化

上部の「音声・演出・進行設定」を開いて操作します。初期値は効果音ON、BGM OFF、音量35%、演出軽減OFFです。OSの`prefers-reduced-motion`がONの場合は、ゲーム内設定にかかわらず演出を軽減します。

`src/progress.ts`が保存を管理します。本番キーは`sort-and-send.progress.v1`、スキーマは次の構造です。個人情報・実行中状態・分岐設定を保存しません。

```json
{
  "schemaVersion": 1,
  "unlockedStageIds": ["01"],
  "clearedStageIds": [],
  "bestStars": {},
  "settings": { "sfx": true, "bgm": false, "volume": 0.35, "reducedMotion": false }
}
```

CLEAR・設定変更・確認後の初期化時だけ保存し、同一内容の書き込みを省略します。評価未確定のCLEARでも次面は解放しますが、未検証の星は作りません。旧版には保存がなかったためCLEARを推測しません。現一覧にないステージIDの記録も保持します。

型・範囲・IDを検証し、壊れたデータは安全な初期状態で再開します。未知のスキーマは解釈せず元データを上書きしません（明示的な進行初期化で保存を再開）。保存不可・容量例外でもメモリ上でプレイを継続し、設定内に状態を表示します。既知の旧スキーマは現時点ではありません。

「進行状況を初期化…」で確認ダイアログを開きます。「キャンセル」やEscでは変更せず、「初期化する」で解放状態・CLEAR履歴・最高星評価だけを消してStage 01へ戻ります。音声・演出設定は保持します。

### 音声・演出

`src/audio.ts`は最初の許可されたユーザー操作後にAudioContextを生成・再開します。到着・誤配送・分岐操作・CLEAR・新記録の合成効果音と控えめなBGMを実装しました。効果音OFF、BGM OFF、音量0を別々に扱い、BGMタイマーは1本だけです。非表示時は停止・ミュート・サスペンドし、再開は次のユーザー操作に合わせます。非対応・生成失敗・再開拒否は無音で継続します。外部音声ファイルはありません。

## 操作

1. 上部の4チャプターに分かれた01〜20ボタンから解放済みステージを選びます。ロック面には直前のCLEAR条件を表示します。面変更では配送状態と全分岐設定だけが初期値へ戻り、進行記録は維持します。
2. HTMLの分岐A〜Eの一覧ボタンから編集する分岐を選びます。各ボタンに現在のパターンを併記し、盤面でも選択中の分岐を強調します。
3. 矢印カードをクリック／タップしてL（左）とR（右）を切り替えます。TabとEnter／Spaceでも操作できます。
4. 「配送開始」で実行します。RUN中は矢印編集、ステージ変更、再挑戦、初期化をロックします。分岐の選択は閲覧用に切り替えられます。
5. 結果で正しく届いた個数と、すべての荷物の配送先を確認します。「再挑戦」で全分岐の設定を保持してDESIGNへ戻り、再度「配送開始」を押します。結果画面でカードを編集してもDESIGNへ戻ります。
6. 「初期設定に戻す」で現在ステージのすべての分岐をLへ戻します。
7. クリア後の「次のステージ」で次へ進めます。Stage 05→06、10→11、15→16も連続して進めます。Stage 20では表示しません。

## 配送ルールと構造

`src/stage.ts`が有向グラフ、荷物ID・色・配送順序、初期パターン、描画用layoutを定義します。`src/simulation.ts`はCanvas／DOMに依存せず、`simulate(stage, patterns)`が経路とイベント履歴を返します。描画座標・画面サイズは配送結果に影響しません。

- 荷物IDの昇順で、0始まりのtickに1個ずつ出発します。
- 各荷物はtick開始時の位置から最大1エッジだけ移動します。出発tickも最初の1エッジのみです。
- 各分岐から送り出す際に現在の矢印を参照し、その分岐のカウンターだけを1つ進めます。最後の枠の次は先頭です。
- 同一tickに同じ分岐から複数荷物を送り出す場合も荷物ID昇順です。
- 各実行で全分岐カウンターを0から開始します。設定・ステージ入力は変更しません。同じ入力から同じ結果・イベント履歴を生成します。
- 出口到着後は移動しません。誤配送があっても残りを継続し、全荷物の到着で終了します。
- 返り値には荷物ごとの経路・配送先・正誤、出発／移動／到着イベント、tick数と集計を含みます。分岐通過履歴はmoveイベントのfrom、direction、patternIndexから取得できます。
- Canvasはシミュレーション済みイベントを時間補間して再生し、フレームレートで配送を判定しません。

`src/validation.ts`で、ノード／荷物ID重複、接続元・接続先、Source数、出口、分岐L/R接続、1〜4枠パターン、配送先、循環、出口に到達できない経路を検証します。この構造検証ではすべての枝を確認します。解法の組み合わせ探索は別モジュールで実行します。不正なステージは開始ボタンを無効にし、レポートへエラーを表示します。シミュレーション入口でも再検証します。

## 解法探索とレポート

`src/solver.ts`の`solveStage(stage, options)`はDOM・描画・localStorageに依存しない非同期関数です。分岐IDをコード単位の安定した昇順に並べ、各枠をLからRの二進順で列挙します。各候補で既存の`simulate`を新規実行し、カウンターを初期化します。通常のゲーム画面では探索しません。

- 総数は`2^(全分岐の枠数合計)`をBigIntで計算します。JSONの`totalConfigurations`は正確な十進文字列です。
- `maxConfigurations`（既定1,000,000件）は0以上の安全な整数。上限に達して未探索候補が残ればINCOMPLETEです。
- `maxStoredSolutions`（既定100件）は保持する成功設定の上限です。0も指定可能で、上限に達しても成功数・最適解数・コスト分布の集計は続けます。
- `signal`にAbortControllerのsignalを渡すとキャンセルできます。64件ごとに制御を返すため、Node.jsの外部処理から実行中に中止できます。
- `VALID`は全探索完了かつ成功解あり、`INVALID`は全探索完了かつ成功解なしです。構造不正は別の`StageInputError`です。
- `INCOMPLETE`の成功数・分布は探索済み範囲の情報です。`minCost`、`maxCost`、`optimalSolutionCount`はnullとし、暫定値を正式な最適値として公開しません。

`reports/stage-validation.json`が開発用の全レポートで、設定とコスト、検証エラーを含みます。`src/generated/stage-ratings.json`はゲーム用集計で、正解設定は含みません。`dist/`に開発用レポートはコピーしません。

`stageFingerprint`はノードID・種類・出口色、分岐枠数、接続、荷物ID順の色列を正規化したJSONにルール識別子を付けた文字列です。ハッシュ衝突を避けるため正規化文字列そのものを識別子とし、layout・board・ラベル・名称・初期矢印値は除外します。配送または採点ルールを変更した際は`fingerprint.ts`のルール識別子も更新してください。

## 方向転換コストと星評価

`src/cost.ts`は循環パターンの隣接方向の変化を数えます。最後から最初への変化も含みます。LLLL=0、LLLR=2、LLRR=2、LRLR=4、LLR=2、LR=2、L=0です。配送イベントで実際に使用した分岐だけを、通過回数に関係なく1回ずつ合算します。

`src/scoring.ts`は配送結果、今回コスト、RESCUE使用有無、ステージと検証済み集計から評価を返す純粋関数です。

- 配送失敗：星0
- 成功・RESCUE使用：星1
- 成功・RESCUE未使用・最適より大きいコスト：星2
- 成功・RESCUE未使用・最適コストと一致：星3
- RESCUE未使用の成功でレポート欠落、不一致、INVALID／INCOMPLETE、集計不備の場合：星数nullの評価未確定
- RESCUE未使用の成功コストが最適値未満／全探索分布に存在しない場合：不整合として星を確定しない

通常配送ではStage 01〜05は各1解で、Stage 07は成功2解とも最適なので成功時は星3です。Stage 06・08・09・10には星2と星3の成功設定があり、同じ荷物列でも経路と周期の組み方で評価が変わります。星1と評価未確定・不整合も単体テストで確認します。通常画面には正解設定や探索詳細を追加しません。

`src/simulation.test.ts`は0.1.0の7件を維持し、Chapter 01の想定解・初期設定、再実行と入力非変更、出発順と二重移動防止、独立カウンターと同時到着順を検証します。`src/validation.test.ts`は正常20面と不正データ、座標からの独立性を確認します。Chapter 02〜04のテストは全探索値・実際の成功解・合流・再現性・一tick一移動を確認します。保存15件、音声5件、演出3件はブラウザ依存処理を模擬して検証します。
